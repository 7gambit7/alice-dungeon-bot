# improvements.md - улучшения алгоритма Алисы

## Предлагаемые улучшения

### 1. Динамическая граница между фазами

Первое, что мне пришло в голову, это отказ от жёсткого `budget = M/2`. Можно переходить в возврат, когда **дальше идти невыгодно**: либо больше нет интересных видимых веток, либо потенциал оставшейся еды на сбор излишков выше, чем на новый ход.

Эвристика: в каждой точке исследования посчитать `returnCost = dist[current → 0]` через посещённые. Если `(M - spent) - returnCost == 0`, заведомо пора возвращаться. Если оставшийся бюджет на один-два хода, а в окружении видимых комнат нет ничего перспективного - тоже пора.


**Плюсы.**
- Адаптивно: на «коротком» подземелье не уходит впустую в дальние ходы; на «длинном» - может идти дальше `M/2`, если уже видит, что путь домой быстрый из-за цикла.
- Не теряет ничего по сравнению с фиксированным `M/2`: всегда обеспечен возврат.

**Минусы.**
- Усложняется логика «когда переходить». Эвристика без обучения легко промахивается.
- Тестирование сложнее: эталон не воспроизводится.

**Когда помогает.** Графы с короткими циклами: исследование может зайти дальше, потому что возврат - это «срез» через цикл, дешевле, чем длина пройденного пути. На дереве разница меньше.

**Когда вредит.** Если эвристика «когда возвращаться» переоптимистична - можно остаться без сборов в фазе возврата (всё съело движение). При плохой эвристике - хуже базы.

### 2. Сбор по суммарной комнатной ценности

Вместо `pickHighestPresent` (макс. удельная ценность среди `count > 0`) использовать `pickHighestRoomTotal`: ищем ресурс с максимальной **суммарной** ценностью в комнате `count[k] * resourceValue(k, target)`.

```cpp
auto pickHighestRoomTotal = [&](int roomId) -> int {
    int best = -1, bestSum = 0;
    for (int k = 0; k < 4; k++) {
        int sum = rooms[roomId].resources[k] * resourceValue(k, target);
        if (sum > bestSum) { bestSum = sum; best = k; }
    }
    return best;
};
```

**Плюсы:**
- Тривиальная замена одной функции, никаких изменений в маршрутизации, парсере, выводе.
- Выигрыш на любых картах, где количество одного ресурса в комнате существенно больше других, что бывает почти всегда (генерации обычно несимметричные).

**Минусы.**
- Меняет поведение на примерах из условия: образцовый пример тогда даст другой вывод. Поэтому это улучшение не для эталонной реализации, а именно для альтернативного бота.
- На редких картах (равные количества и явно доминирующий по удельной ценности один ресурс) разница нулевая.

**Когда помогает.** Любая «реалистичная» генерация ресурсов, где числа отличаются хоть как-то. Особенно: комнаты с большим количеством iron/exp и единичными gems.

**Когда вредит.** Практически никогда. Контр-пример сконструировать можно (iron=1, gold=1, gems=1, exp=1 - обе стратегии эквивалентны), но систематических потерь нет.

### 3. Добор ресурсов в комнате при исследовании (немного сомнительный)

В фазе исследования, после бесплатного первого сбора, оценить выгодно ли заплатить 1 еды за следующий ресурс **здесь и сейчас**. Простейшее правило: «добирать пока в комнате есть ресурс с ценностью ≥ ожидаемая ценность одного хода исследования».

«Ожидаемая ценность одного хода» - некоторая средняя ценность ресурса в новой комнате. В В целом как вариант либо подсчитать как `avg(resourceValue * count)` по уже посещённым, либо взять глобальный порог (например, 12 - между gold и iron). Альтернатива без оценки: «добирать всё, что > T», где `T` фиксированный.

```cpp
// после бесплатного сбора в комнате:
while (true) {
    int bestRes = pickHighestRoomTotal(current);
    if (bestRes < 0) break;
    int gain = rooms[current].resources[bestRes] * resourceValue(bestRes, target);
    if (gain < THRESHOLD) break; // дальше брать невыгодно
    if (spent + 1 > budget) break; // не выйти за бюджет
    // оплачиваемый сбор:
    doCollect(current, bestRes); // spent++
}
```

**Плюсы.**
- Часто две порции ресурсов в одной комнате выгоднее, чем «бесплатная» в одной + ход в соседнюю и «бесплатная» там - особенно если соседняя комната окажется бедной.
- Линейно по числу ресурсов, никакой комбинаторики.

**Минусы.**
- Съедает бюджет исследования, бот доходит до меньшего числа новых комнат. На богато-разреженных картах (одна-две комнаты с горой ресурсов и куча пустых) это окей, но на однородных картах теряем коридор покрытия.
- Правильный `THRESHOLD` зависит от ожиданий по будущим комнатам - точную «среднюю» бот не знает.

**Когда помогает.** Карты с большой неоднородностью «жирных» и «бедных» комнат. Когда бесплатный сбор уже взял gems в богатой комнате, а рядом 100 iron, без добора их теряем.

**Когда вредит.** Однородные карты: бот сжигает еду на «средние» ресурсы и не доходит до удалённой комнаты, где могло быть лучше.

### 4. Маршрутизация с учётом структуры видимых комнат

В правиле выбора непосещённого соседа добавить вторичный приоритет: при нескольких кандидатах предпочитать ту видимую комнату, у которой больше известных соседей (т.е. бОльшая часть подземелья за ней разведана). Альтернативно - предпочитать комнаты, чья степень в графе больше (вероятный «хаб»).

**Плюсы.**
- Бот ведёт себя как «исследователь, а не маршрутизатор по id»: тянется в направления, обещающие больше последующего выбора.
- Дешёвая надстройка над текущим правилом, без полного перехода на оптимизацию.

**Минусы.**
- Это всё ещё эвристика - степень коррелирует с «полезностью» неидеально.
- Может предсказуемо проигрывать на специально сконструированных картах, где «хаб» бедный, а тупик - богатый.

**Когда помогает.** Подземелья с явной топологией «коридор + хаб»: бот сначала идёт в хаб и оттуда веером смотрит на ветки.

**Когда вредит.** «Бедные хабы»: высокая степень, но никаких ресурсов.

### 5. Возврат через «жирные» комнаты - детур

В фазе возврата вместо строго кратчайшего пути можно искать маршрут «кратчайший + крюк», максимизирующий ожидаемую ценность сбора. То-есть, условно среди всех путей из `current` в `0` длины ≤ `M - spent`, проходящих по посещённым комнатам, найти тот, по которому суммарная ценность собираемых ресурсов (с учётом стоимости каждого «не-первого» сбора в комнате) максимальна.

В общем, вариант упрощения - это жадно искать **одну** «жирную» посещённую комнату на расстоянии `d` в сторону от кратчайшего пути, крюком зайти в неё, если `2d + cost_сборов ≤ оставшаяся еда` и итоговый прирост ценности положителен.

**Плюсы.**
- Прямая атака на самое неэффективное место текущего алгоритма: слепая трата излишков в первой попавшейся комнате.
- Сохраняет инвариант возврата: бот гарантированно доберётся до 0.

**Минусы.**
- Главная сложность - точная оптимизация дорогая.
- Меняет логику возврата сильнее всех остальных пунктов, осложняет тестирование.

**Когда помогает.** Подземелья с длинными «жирными» ветками, в которые мы зашли по исследованию и не успели всё собрать.

**Когда вредит.** Линейные цепи: альтернативных маршрутов нет, детур невозможен, оверхед нулевой, но и улучшения нет, так что в таких случаях бессмысленно.
